# Token Storage on Public Clients

RFC 6749 splits clients into two kinds, and the split is not about platform but
about capability: a **confidential** client can keep a secret, a **public** one
cannot. An Android app, a single-page app and a CLI are all public clients,
because anything shipped to the user can be decompiled, inspected or dumped from
memory. Every storage decision below follows from accepting that, rather than
trying to engineer around it.

## The two client types

| | Confidential | Public |
|---|---|---|
| Examples | Server-side web app, daemon | Mobile, SPA, desktop, CLI |
| Can hold a client secret | Yes | **No** |
| PKCE | Recommended | **Mandatory** |
| Credential lives | On a server you control | On the user's device |
| Compromise scope | Every user at once | One device |

The last row is the one people miss. A public client's blast radius is smaller
than a backend's, which is a genuine argument in favour of the client-only
architecture — see [[API - Client-Only vs Backend Architectures]].

## Where the token can live

| Platform | Do this | Never this |
|---|---|---|
| Android | Keystore-wrapped ciphertext on disk | `SharedPreferences` in cleartext |
| iOS | Keychain, with an accessibility class | `UserDefaults`, plist |
| Browser | In memory, or a `Secure; HttpOnly` cookie | `localStorage`, `sessionStorage` |
| Desktop | OS keychain (Keychain, DPAPI, Secret Service) | A dotfile in the home directory |
| CLI | OS keychain, else a `0600` file, stated plainly | An env var in shell history |

The browser row is the sharpest: `localStorage` is readable by any JavaScript on
the origin, so one XSS is total token theft. An `HttpOnly` cookie cannot be read
by script at all, which is why it survives XSS that `localStorage` does not.

## Android: what the Keystore actually guarantees

The Keystore does not store your token. It stores a **key** that never leaves
hardware-backed storage, and you keep the ciphertext yourself. Extraction of the
app data directory therefore yields bytes that are useless off-device.

```kotlin
private const val KEY_ALIAS = "github-token"

private fun secretKey(): SecretKey {
    val store = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    (store.getEntry(KEY_ALIAS, null) as? KeyStore.SecretKeyEntry)
        ?.let { return it.secretKey }

    val spec = KeyGenParameterSpec.Builder(
        KEY_ALIAS,
        KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT,
    )
        .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
        .setUserAuthenticationRequired(false)   // true = requires device unlock
        .build()

    return KeyGenerator
        .getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
        .apply { init(spec) }
        .generateKey()
}
```

```kotlin
fun encrypt(token: String): ByteArray {
    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    cipher.init(Cipher.ENCRYPT_MODE, secretKey())
    // The IV is generated by the cipher and must be stored with the payload.
    return cipher.iv + cipher.doFinal(token.toByteArray())
}

fun decrypt(blob: ByteArray): String {
    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    val spec = GCMParameterSpec(128, blob, 0, 12)
    cipher.init(Cipher.DECRYPT_MODE, secretKey(), spec)
    return String(cipher.doFinal(blob, 12, blob.size - 12))
}
```

> [!tip] Bind the key to the lock screen
> `setUserAuthenticationRequired(true)` makes the key unusable until the user
> authenticates, which is what turns "stolen phone" from a compromise into an
> inconvenience. The cost is handling the key being invalidated when the user
> changes their lock screen or enrols a new biometric.

## Threat model

| Threat | Does the Keystore help? | What actually helps |
|---|---|---|
| Lost or stolen locked device | Yes | Bind the key to user authentication |
| Backup or `adb` extraction | Yes — ciphertext only | Disable backup for the token file |
| Malware running as root | **No** | Short token lifetimes, fast revocation |
| Token in logs or crash reports | No | Never log the header. See gotchas |
| Screenshots, recents thumbnail | No | `FLAG_SECURE` on sensitive screens |
| Reverse engineering the APK | Not applicable | Ship no secret to reverse |

The honest summary: on-device storage defends against an attacker who gets the
*files*. It defends against nobody who gets *execution* as your app. Storage
hardening is necessary and never sufficient.

## Shrinking the blast radius

Storage is one of three controls, and the weakest of them:

- **Scope.** A token that can only read is worth far less than one that can push.
  Request the narrowest scope the feature needs — see [[API - OAuth 2.0 Flows]].
- **Lifetime.** Short-lived access tokens plus rotating refresh tokens mean a
  stolen copy expires on its own. A classic personal access token does not
  expire, which is what makes it the worst thing to keep on a device — see
  [[GitHub - Authentication]].
- **Revocation.** The user needs a working "sign out everywhere", and the client
  must treat a 401 as "discard and re-authenticate" rather than retrying — see
  [[API - Idempotency and Retries]].

## ⚠️ Gotchas

- ⚠️ **Never ship a client secret in an app.** It is extractable from the APK in
  minutes, and a secret every install shares is not a secret. This is the entire
  reason PKCE exists.
- ⚠️ **An HTTP logging interceptor will print the `Authorization` header.**
  Leaving one at header or body level in a release build writes tokens into
  logcat and into every crash report. Gate it to debug builds and redact the
  header explicitly.
- ⚠️ **Application backup is on by default.** Without excluding your token
  storage from backup, the file leaves the device entirely. Keystore ciphertext
  limits the damage; do both.
- ⚠️ **`localStorage` plus one XSS is full account takeover.** For web public
  clients this is the most exploited storage mistake there is.
- ⚠️ **Keystore keys can be invalidated out from under you.** Changing the lock
  screen or enrolling a biometric can destroy the key permanently, and your
  stored ciphertext becomes unreadable. Catch it and re-authenticate instead of
  crashing on every launch.
- ⚠️ **A rooted or compromised device wins.** The Keystore will decrypt for
  whoever runs as your app. Treat storage as raising cost, not as a boundary.
- **Keep the token out of environment variables and shell history** on desktop
  and CLI clients. `ps`, history files and CI logs all leak it.
- **Do not sync the token across devices.** Cloud-synced storage turns one
  device compromise into all of them.
